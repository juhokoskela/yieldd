# Runner boundaries

The VM boundary separates a local workflow from the Mac's processes and files. yieldd does not share host directories with either guest. This assumes the hypervisor, its devices, Apple Container's host service, and SSH work as designed. It does not assume that anything inside the guest remains trustworthy after a job starts.

Linux jobs run as `runner` with passwordless `sudo` inside their disposable guest. Host permissions are unchanged. Rebuild the Linux guest image to enable this for new guests.

Guest commands have bounded output capture, including Linux shutdown helpers. Diagnostic rendering escapes terminal controls, Unicode format characters, and default-ignorable characters, including bidirectional overrides and zero-width characters. Captured bytes remain unchanged for protocol parsing. Connected execution needs renewable coordinator authorization: five minutes without a renewal causes host-side destruction, while a healthy job can keep renewing without a total duration limit. Capacity is released only after destruction succeeds. Guest status remains useful progress information, not execution authority. Standalone `serve` and `agent` do not use coordinator authorization; this change does not impose a new total duration limit on them.

JIT configuration accepts only `.runner`, `.credentials`, and optional `.credentials_rsaparams`, with base64 contents. It checks the expected runner name, ephemeral setting, and `_work` folder. These checks are not independent proof of repository membership. The coordinator is still trusted to choose the workload and supply genuine GitHub credentials. A local repository-name check alone would not protect against a compromised coordinator supplying forged metadata and another runner's credentials. Independent enrollment needs an authority separate from that coordinator.

Hosted fallback is not a nested sandbox. Its job runs as the provider's account and can affect anything that account can access. Select a provider that destroys the host after each bootstrap. Do not send hostile jobs to a persistent fallback machine.

## Host controls and limits

NAT is not a host or LAN firewall. Stock Apple Container machines can reach networks exposed by the Mac, including reachable host services. Linux runner commands now require the [pinned Container fork](linux-runner-network.md), which attaches only to the relay. An [upstream report](https://github.com/apple/container/issues/1320) also describes vmnet traffic bypassing ordinary macOS firewall filtering. That report is not validation of a filter on this host. yieldd does not install firewall rules.

The [network-isolation investigation](runner-network-isolation.md) describes host access through the stock Linux runner-machine path. The [Linux integration runbook](linux-runner-network.md) describes configuration verification before headless boot, recovery, and relay-loss handling. Its [validation boundary](linux-runner-network.md#validation-boundary) tracks current acceptance coverage.

macOS `machine-test`, `runner-test`, `serve`, the agent, and connected runners now attach only to the relay. SSH uses a private Unix socket with the template's pinned host key. The sockets live under macOS's user-private temporary directory, so another local user cannot pre-create their directories or occupy the SSH forwarder's connection slots. Processes under the yieldd account remain trusted. Relay startup failure prevents VM startup. Relay loss cuts networking, with no NAT fallback; host checks detect it during startup and before commands, and existing SSH connections close with the relay. Cleanup attempts both relay termination and VM destruction within the shutdown budget, retaining the cleanup obligation and capacity when either fails. Owner death closes the relay's lifetime pipe. Both standalone and connected recovery remove abandoned socket directories using the state directory and runner identities, without signaling stored PIDs. The manual `agent vm-probe` still uses NAT and is not for hostile jobs.

Linux-only `connect` still recovers recorded macOS assignments, but skips the macOS orphan sweep. Use `recover` or start a macOS slot to sweep unleased macOS clones and socket directories. Invalid socket entries are reported without preventing other orphan removals or independent clone cleanup.

Relay summaries identify the runner and distinguish policy refusals from malformed traffic, DNS saturation, and resolver failures. Interval counts and bounded repeat tracking help identify retry loops without logging guest names, addresses, packet contents, or fingerprints. Repeated refusals are not evidence of hostile intent. Reporting is best effort and cannot delay networking or process shutdown.

The relay filters private and current host destinations and drops IPv6. It sends guest DNS to a fixed public resolver through its destination check, not through the Mac's LAN/VPN resolver or mDNS. Permitted Internet traffic, including public DNS, can still carry arbitrary data. Public-address hairpin routes and interface changes affecting established connections remain limitations. Relay CPU, memory, and connection budgets are not yet enforced.

Sparse guest disks and APFS clones do not impose a storage quota by themselves. New guests now require a configured, quota-limited APFS volume for Apple Container data, guest-generated logs, macOS templates, and clones. Recovery journals stay on another filesystem. [Storage setup](runner-storage.md) is explicit: it does not move existing data or reconfigure a running Container service. Apple Container's data root is service-wide and may include non-yieldd machines.

The filesystem enforces the quota without relying on guest reports or host polling. A full guest volume can still break jobs and Container's own metadata writes; unresolved cleanup remains recorded outside it. This does not reserve host free space or protect against unrelated host writers. No disk migration or privileged setup is performed automatically.

The coordinator container now uses bridge networking, publishes only a loopback port, and has CPU, memory, and process limits. Non-loopback HTTP binding is rejected unless explicitly enabled with `--allow-non-loopback-client-listen`, which Compose supplies. The flag acknowledges the risk; it does not verify container isolation or port publication. Bridge networking reduces access to host-loopback services and resource use, but does not provide an outbound LAN deny policy. The bearer token and GitHub credentials still require protection on both endpoints.
